### Live queue (2026-08-07, superseded by the entry above) — Self-hosted licensing: license-gated release distribution, not raw git access (`2ab3919`)

Direct follow-up to the billing session below: the user asked how a self-hosted school actually gets code updates, since pushing to this repo's `main` never reaches a separate self-hosted deployment. Recommended (2-3 sentence exploratory answer, not built yet) reusing the existing license-check mechanism as the distribution channel instead of raw git/GitHub access, plus was honest that no technical fix stops someone from copying PHP source once it's on their own server — the real protection there is a legal license agreement, not code. User said "yes" to planning the release-package + license-gated-update piece. Went through full Plan Mode: 2 parallel Explore agents (the existing licensing infrastructure end to end; the backup/archive-generation and signed-URL patterns already in this codebase), one `AskUserQuestion` to confirm download-only vs auto-apply, `ExitPlanMode` approved.

**A real, live bug found during research and fixed as part of this**: `POST /api/license/verify` (`LicenseVerifyController`) lived in `routes/web.php`, which applies Laravel's default `web` middleware group — CSRF included. A genuine external self-hosted server's check-in has no CSRF token and would 419 in production; the existing `SelfHostedLicenseTest` only ever passed because PHPUnit's own test client auto-bypasses CSRF in testing mode, which doesn't happen for a real request. This has been silently broken since the self-hosted licensing feature shipped on 2026-07-18 — nobody had tried a genuine unauthenticated HTTP call against it until this session. Fixed by introducing a proper `routes/api.php` (wired into `bootstrap/app.php`'s `withRouting(api: ...)`, Laravel's stateless `api` middleware group, no CSRF, automatic `/api` prefix) and moving `license.verify` there — the automatic prefix means the URL is unchanged (`/api/license/verify`), so no already-configured self-hosted install's `SKULOS_LICENSE_ENDPOINT` breaks.

**Built**: `App\Models\Release` (version/notes/file_path/file_size/checksum/published_at, platform DB only) + `App\Services\Licensing\ReleaseService::build()` — runs a real `git archive --format=zip HEAD -- backend` against the platform server's own working copy (it already **is** a git checkout of this exact repo), computes a real sha256, stores via `Storage::disk('local')` matching the exact path convention `Backup`/`BackupService` already use. New `Admin\ReleaseController` + `resources/views/admin/releases.blade.php` (build/publish/unpublish/delete/download), linked from the Settings hub alongside Self-Hosted License. `LicenseService::verifyIncoming()` extended (additive only) with `latest_version`/`latest_release_notes`/`latest_release_checksum`, bundled into the existing hourly check-in response rather than a second round trip. New `ReleaseDownloadController` (`routes/api.php`, license-key-authenticated exactly like `verify()` already is — a revoked/expired license loses download access the same way it already loses runtime access) with `latestRelease()`/`download()`. Self-hosted side: `schools.latest_available_version` (set by this install's own check-in), `config('skulos.version')` (this install's own current version, `SKULOS_VERSION` env, set manually as the last step of applying an update), an "Update available" banner on the existing self-hosted license settings screen, and `LicenseSettingsController::downloadUpdate()` — downloads the release, verifies its sha256 against what the platform reports (mirrors `BackupService::restore()`'s own "verify before trusting" discipline — a corrupted/tampered transfer is discarded, never left half-saved), and stops there.

**Deliberately download-only, per the confirmed design decision**: nothing is ever auto-extracted, composer-installed, or migrated. `DEPLOYMENT.md`'s "Updating an existing self-hosted install" section (already written in the prior session) was rewritten to describe the real flow: download via the license-gated button → extract manually → `composer install` → `migrate --force` → set `SKULOS_VERSION` in `.env` → confirm `license:check` still runs clean. A `git pull`-based fallback is documented too, for the platform's own staging/dev environment which does have direct git access.

**QA**: new `ReleaseTest.php` (7 tests, genuinely shells out to real `git archive` against this actual repo, not mocked — `Storage::fake('local')` redirects the real file write into throwaway test storage so nothing is left behind in dev). `SelfHostedLicenseTest.php` extended with 6 more tests (release info correctly bundled into/omitted from the verify response, `checkOne()` stores the latest available version, the settings-page banner shows only when versions genuinely differ, `downloadUpdate()` saves on a checksum match and discards+errors on a mismatch, via `Http::fake()`). Full unfiltered `php artisan test`: 1427 passed, 2 failed — both the same pre-existing, already-confirmed-unrelated failures from earlier this session (the "Assignments bypasses module gating" nav bug), zero regressions from the `bootstrap.php`/routing change across the entire suite.

**Live-verified end to end with real, unauthenticated HTTP requests** (the one thing PHPUnit's own CSRF bypass can never prove): confirmed the CSRF fix directly — a raw `curl -X POST /api/license/verify` with no session/CSRF token at all now returns a real 200 JSON response instead of 419. Built a real release through the real admin screen (a genuine 8.8MB `git archive` of this actual codebase, real sha256), published it, created a real self-hosted-flagged test school with a real issued license key, then called `verify`/`latest-release`/`download` exactly as a genuine self-hosted server would: the check-in correctly reported the new version, the download streamed the real zip, and the locally-computed sha256 of the downloaded file matched the platform-reported checksum exactly. Revoked the license and confirmed download access was cut off immediately (403, `unknown_license_key`) — the same incentive that already gates runtime access now gates updates too. ### Live queue (2026-08-07, superseded by the entry above) — Billing: free-term waivers now actually waive billing + per-school/bulk price override

Direct follow-up to the pre-launch readiness check below: the user quoted my own finding back ("There's no automatic '1 term free' plan... every trial is manually reviewed... who can waive a term's billing afterward on a case-by-case basis") and said "fix this so that the platform owner/admin can give it to a school," plus asked for a way to change a school's cost per student per term, individually or in bulk. Went through Plan Mode (one Explore agent to sweep every `price_per_student_per_term` call site and confirm the established bulk-select UI pattern, `ExitPlanMode` approved).

**Real bug found: waivers didn't do anything.** `Admin\BillingController::addWaiver()` created a `BillingWaiver` row (a label/note), but nothing anywhere — `SubscriptionService::amountDue()`/`billingSnapshot()` — ever read it. An admin "marking a term free" had created a cosmetic note; the school's `next_billing_date` never moved and the amount shown as due never changed. Fixed properly: `addWaiver()` now takes a `days` field and, in one transaction, creates the `BillingWaiver` row, pushes `next_billing_date` forward by that many days (same base-date logic `SubscriptionController::extend()` already uses), logs a real `SubscriptionEvent` (new `TYPE_WAIVER`), and reinstates the school if it was locked out for billing — the same courtesy `renew()` already gives a school that pays, since waiving is functionally equivalent to paying. `removeWaiver()` deletes the record only, deliberately does not reverse the date push (documented as a known limitation, corrected the same way any other billing action is corrected).

**New per-school + bulk price override**: new nullable `schools.price_per_student_per_term_override` column — null (every existing school, unchanged) falls back to the assigned Plan's price; a school's own override, when set, replaces it for billing purposes only, never touching the school's feature/module set (that stays entirely Plan-driven). New `SubscriptionService::effectivePrice()` is now the one real call site `amountDue()`/`billingSnapshot()` both go through (confirmed via a full sweep: no other call site needed updating). New single-school (`Admin\BillingController::updateSchoolPrice()`) and bulk (`bulkUpdateSchoolPrice()`, reusing the exact established bulk-checkbox UI pattern from `school.houses.index`/`admin.schools.index`) actions on the Billing page's own Schools table, a new "Price / term" column showing the effective price with an inline per-row edit form.

**A second real bug found live, not by inspection**: the very first live HTTP test of the new waiver action threw a real 500 — `Carbon::rawAddUnit(): Argument #3 ($value) must be of type int|float, string given`. Laravel's `'integer'` validation rule only checks the format, it never casts; a genuine HTTP request body is always a string, so `addDays($data['days'])` got a numeric string, not an int. **This exact same bug was already latent in the pre-existing `extend()` action too** — it stayed hidden in `SubscriptionTest` because PHPUnit's own test client passes native PHP array values (a literal `int` stays an `int`), never exercising the real string-from-HTTP-body path a genuine request always takes. Fixed both with an explicit `(int)` cast, with a comment explaining why the existing test suite never caught it.

**QA**: extended `BillingTest.php` with 6 new tests (waiver actually pushes the due date + creates a real `SubscriptionEvent`, waiver reinstates a billing-locked school, single-school override + clearing it back to the plan price, bulk override across N schools leaves untouched schools untouched, a school with no override at all is billed at exactly its plan's price). Full `Billing*`/`Subscription*`/`ManageModules`/`PlanFeatureNav`/`PlatformDashboard`/`SchoolAdminManagement` sweep re-run together, 39/39 (later 59/59 including the first pass) passing, 0 regressions.

**Live-verified for real on the running dev server, not just tests**: logged in as a real platform super admin, set a real custom price override on greenfield (confirmed `effectivePrice()`/`amountDue()` both reflected it, confirmed both the Billing page and the school's own Manage page showed "Custom" correctly), cleared it back to the plan price, confirmed the fallback. Created throwaway test schools, submitted a real waiver via HTTP (this is what caught the Carbon TypeError), confirmed after the fix that `next_billing_date` genuinely moved by the exact day count and a real `SubscriptionEvent` existed with the right note. Submitted a real bulk price-override request across two test schools, confirmed both picked it up. All test schools/events/waivers removed afterward; confirmed greenfield's own real `next_billing_date`/override were completely untouched by any of this verification.

### Live queue (2026-07-30, announcement/broadcast emails now queued, not sent inline — Codex audit item 2)

After the report card revert, user said "CONTINUE" — moved to the next item on the priority list I gave them (mobile table-stacking was item 1, now done): synchronous bulk email/broadcast sends, a real timeout risk for a large "all audience" send, not theoretical (a school-level announcement to "all" can plausibly reach 500-3,000+ recipients; the platform admin broadcast multiplies that across every matched school in one request).

Found two inline `Mail::send()` loops: `CommunicationService::emailAnnouncement()`/`sendEmail()` (school-level announcements/broadcasts, feeding `AnnouncementController::store()` and `MessageController::store()`), and `Admin\BroadcastController::send()` (the platform-wide leadership broadcast, the worse of the two since it loops every matched school). Neither `app/Jobs/` nor any `ShouldQueue` implementation existed anywhere in the codebase before this, net new pattern.

**Fixed**: two new jobs, `SendAnnouncementEmailJob` and `SendPlatformBroadcastEmailJob`, both `ShouldQueue`. `CommunicationService` now creates each `CommunicationLog` row (already had a `STATUS_QUEUED` status that was set but never actually meant, a synchronous send followed almost immediately) and dispatches a job per recipient instead of calling `Mail::send()` inline; `BroadcastController::send()` does the same. A queue worker has no "current tenant" at all when it picks up a job, unlike an HTTP request (`ResolveTenant` middleware never ran), so `SendAnnouncementEmailJob::handle()` explicitly resolves the `School` from the platform DB and calls `TenantManager::connectTo()` itself before touching the tenant-scoped `CommunicationLog`. Also handled a subtler correctness issue: `MailSettingsService` (admin-configurable SMTP, 2026-07-09) works by mutating `config('mail.*')` in place, fine for one request but a persistent `queue:work` process stays booted across many jobs for many different schools, so a school with no SMTP override of its own could silently inherit whatever the previous job in that worker last configured. Both jobs now reapply `applyPlatformDefaults()` (+ `applySchoolOverride()` inside the tenant connection, for the school-level job) fresh on every single send, mirroring the same order `ResolveTenant` runs at request time.

**Deployment**: added `Schedule::command('queue:work --stop-when-empty --max-time=50')->everyMinute()->withoutOverlapping()` to `routes/console.php`, piggybacking on the existing `schedule:run` cron entry every cPanel deploy already needs (per `DEPLOYMENT.md`) rather than requiring a second cron line or a persistent daemon shared hosting can't run anyway. `--stop-when-empty` matters here specifically because this invocation is a fresh process every minute, not a long-running worker. `DEPLOYMENT.md` updated to describe this instead of the now-inaccurate "everything sends inline, no queue worker needed" paragraph it had.

**Return value semantics changed on purpose, not just internally**: `emailAnnouncement()`/`sendEmail()`/`dispatchAnnouncement()` used to return real `sent`/`failed` counts, honest under the old inline-send code, since the counts were known by the time the method returned. Under a real queue driver in production, nothing has actually been sent yet when these methods return, only enqueued, so reporting `sent`/`failed` there would now be a fabricated, misleading number (the standing "no fabricated success" rule). Renamed to `queued` everywhere (`CommunicationLog` itself still ends up `sent`/`failed` once its job actually runs, that part of the truth isn't lost, just no longer knowable synchronously). Flash messages on both `AnnouncementController::store()` and `MessageController::store()` now read "X email(s) queued to send" instead of "X emailed"; the platform broadcast's flash message similarly says "queued to N recipient(s)" instead of "sent to".

**QA**: `CommunicationTest`/`NotificationDispatchTest`/`PlatformBroadcastTest`/`MessageBroadcastTest`/`AnnouncementComposeTest`/`CommunicationHistoryTest` all re-run, 47/47 passing (the existing `Mail::assertSent()` assertions kept working unchanged since `phpunit.xml` already set `QUEUE_CONNECTION=sync`, meaning a dispatched job still runs inline within the same test process, so this was a safe refactor to make without needing to rewrite most existing tests to `Queue::fake()`). Two genuinely new tests added specifically because the sync driver's inline execution would otherwise mask the real behavior change: `test_publishing_dispatches_one_queued_job_per_recipient_instead_of_sending_inline`/`test_broadcast_dispatches_one_queued_job_per_recipient_instead_of_sending_inline` use `Queue::fake()` to prove the send is a genuinely separate queued unit of work, not synchronous code that only happens to look queued; `test_the_job_establishes_its_own_tenant_connection_when_run_with_none_active` explicitly forgets the tenant connection before running the job (the real blank state a worker starts from) and confirms it still resolves the right school, updates that school's own log, and restores no-tenant state afterward rather than leaking the connection.

### Live queue (2026-07-30, backup restore made safe — a real hazard from an external Codex code/UI audit)

The user ran a separate Codex agent against this same repo for a read-only UI/UX audit, code audit, and a FEEDBACK LIST cross-check (that last one was still running when the user pasted its transcript here). **Fixed** (`7e039ab`): `BackupService::restoreMysql()` used to `DROP DATABASE` the live tenant database, THEN import the backup — if the import failed partway, the school was left with an empty database and no way back. The SQLite path had the same shape of bug: it overwrote the live `.sqlite` file directly with `file_put_contents()`, so a corrupt/truncated backup file could leave the live file broken. Both now write-verify-swap instead:
- **SQLite**: restore into a temp file (`{target}.restoring-{uniqid}`), run a real `PRAGMA integrity_check` against it, only `rename()` it over the live file (a single directory-entry swap, not a byte-by-byte overwrite) if that passes. Any failure cleans up the temp file and throws, live file untouched.
- **MySQL**: import into a throwaway `{db}_restoring_{timestamp}` database first. Only once `mysql` actually succeeds does `swapMysqlDatabase()` move it into place, via one atomic multi-table `RENAME TABLE` statement (MySQL has no `RENAME DATABASE`). The live database's own current tables are moved aside into a timestamped `{db}_before_restore_{Ymd_His}` database first — a real safety net, deliberately kept rather than dropped, at the cost of disk space until an admin or a future retention job clears it — not thrown away until the new data is already confirmed in place.

Both restore controllers (`School\BackupController`, `Admin\BackupAdminController`) now catch a failed restore and flash a clear `session('error')` message instead of a raw 500, since a failed restore is now a normal, recoverable outcome, not something that should never happen.

New regression test `test_restoring_a_corrupt_backup_file_leaves_the_live_database_untouched` proves the failure path actually protects live data (asserts a student created before the botched restore attempt is still there afterward). `BackupRestoreTest` 8/8 green, including the pre-existing happy-path restore test (proving the new rename-swap still actually restores data correctly, not just safely). **The MySQL path could not be tested directly** — this dev environment has no MySQL (SQLite stands in for it locally, per the "Local environment reality" section below) — so `swapMysqlDatabase()`'s `RENAME TABLE`/`SHOW TABLES FROM` SQL was hand-verified against real MySQL syntax rather than executed. ## Working conventions

- **Text on a colour must always be readable, never assume dark text works** (user report 2026-07-11, a screenshot of a "Resume" button with unreadable black text on a dark green background). Since a school picks its own brand colour (the swatch grid/native picker on Branding), any text rendered directly on `var(--accent)` can no longer assume the old fixed dark ink (`#241503`) always reads well, a school that picks a dark colour (navy, purple, black, brown) with hardcoded dark text becomes unreadable. Fixed via `App\Support\ColorContrast::inkFor()` (WCAG relative luminance, picks black or white), wired into `layouts/app.blade.php` as a `--accent-ink` CSS variable alongside `--accent`; every place styling text on top of `var(--accent)` must use `color:var(--accent-ink)`, never a hardcoded hex. This does not apply to the platform's own fixed, non-configurable design colors (`--ok`, `--warn`, `--bad`, the dashboard's hand-picked figure-card colors), those are chosen by us and already paired with a colour that works.
- **Database and storage efficiency is a standing design constraint, not a later optimization pass** (from the user's "Dbase recommendation.docx", read in 2026-07-11: "take note of my Dbase recommendation for all your previous, current and future builds"). The MVP launches on shared cPanel/MySQL hosting, so build with that ceiling in mind from the start: never store file bytes in the database (path/reference columns only), compress and convert uploaded images to WebP at upload time, never keep generated PDFs (report cards, receipts, certificates) forever, prefer generate-on-demand or a configurable retention window, paginate every list screen, select only needed columns, and give anything that grows unbounded (logs, notifications, sessions, temp uploads) a retention/cleanup policy. Full standing rule list and current build status for each item: DEVELOPMENT_TRACKER.md's "Database & Storage Efficiency Rules" section, near the top.
- **Every list/index screen gets bulk actions, not just single-row ones** (user directive 2026-07-11, given after the houses reactivate bug report: "add a bulk option to do the reactivate, delete, retire at once with a check box... this is the way I want every of my builds to look like"). Any screen that lists rows a user can act on one at a time (retire, reactivate, delete, assign, etc.) should also let them tick several and act on all of them in one request, not just one row at a time. Reference implementation: `school.houses.index` (`backend/resources/views/school/houses/index.blade.php` + `HouseController::bulkAction()`), built 2026-07-11. Pattern: a per-row checkbox named `thing_ids[]`, a header "select all" checkbox, and an action bar of submit buttons, all wired via the HTML5 `form="idOfBulkForm"` attribute pointing at an out-of-band `<form id="idOfBulkForm">` placed outside the `<table>`, not wrapping the table in its own `<form>`. This matters because existing per-row single-action forms (a "View" link, a "Retire" button, a "Remove" button) already live inside each row's `<td>`, and HTML forms cannot nest, so the bulk checkboxes must associate with their form by `id`/`form` attribute rather than physical nesting. A small vanilla script (no framework) handles "select all" and a "tick at least one first" guard before submit; the server route validates `min:1` regardless. Apply this pattern going forward to Students, Staff, and any other list screen as they get bulk-eligible actions, rather than building single-row-only controls and needing to retrofit bulk support later.
- **No dashes in on-screen text** (user directive 2026-07-08, restated firmly). User-facing copy must not use hyphens or em/en dashes as punctuation — the user considers it an "AI-generated" tell. This includes text rendered via **CSS `content:` values** and **`aria-label`/`title`/`alt` attributes**, not just `>text<` nodes. When sweeping, check all three: text nodes, CSS `content`, and rendered attributes. Code comments do not render and are exempt. Verify with byte-level checks using unicode escapes (`—` em, `–` en), not literal characters piped through a shell — the shell can mangle the char so a naive check reports a false "0 remaining" (this bit us once on 2026-07-08). **Exemption confirmed 2026-07-10:** a hyphen inside a standard, correctly-spelled compound term (e.g. "Pre-Nursery") is fine — the rule targets dashes used as clause-separating punctuation (the "AI tell"), not hyphens that are genuinely part of how a word is normally spelled. When in doubt whether a term is "standard," ask rather than silently rewriting it (e.g. to "Pre Nursery") or silently leaving it as is.
- **No section sign character anywhere** (user directive 2026-07-10). Spell it out: write "section 14" rather than the symbol form. Applies everywhere, including planning docs like the tracker and this file, not just product UI copy.
- **Thorough QA after every item build** (user directive 2026-07-08). After finishing each build item, before declaring it done, run a real QA pass and record it in the tracker: (1) run tests / exercise the actual behavior, note issues, bugs, DB errors; (2) ask and answer honestly: *Did I fully solve what the user asked? Did I miss anything they requested? Did I change or break something I should not have touched? Is anything half-done or faked?* Fix what QA surfaces before moving on. - **Nothing hardcoded — ever** (user directive 2026-07-08, reinforcing docx TD-007 / "Configuration Before Customization"). Anything a school or the Platform Super Admin could plausibly want to change — pricing, plan features, grading formulas, role permissions, module lists, contact details, copy, term counts, thresholds — must live in config, the database, or admin-editable settings, never as literals baked into code paths. The `config/skulos.php` catalog + per-school `settings` table + module/permission tables are the sanctioned homes for this. If you find yourself typing a business value into a controller or view, stop and move it.
  - **Restated more precisely 2026-07-12, after the score-range comment bank was first built reading straight from `config('skulos.default_comment_bank')` with no way for a school to edit it:** "everything must be a DB-backed layer, which means an admin/school/user should be able to customize their own." - **Domain routing + route parameters gotcha (found 2026-07-09, recurred and re-fixed the same day in `BackupController`).** On any route under `Route::domain('{school}.'.$domain)` that also has its own path parameters (e.g. `/campuses/{campusId}`), do **not** declare those as typed method parameters on the controller action (`function destroy(Request $request, string $campusId)`). Laravel resolves untyped/scalar controller parameters **positionally** against the full route parameter list, domain parameter included, not by name — so `$campusId` silently receives the school's slug instead. It fails quietly: `findOrFail()` on the wrong value throws `ModelNotFoundException`, which Laravel renders as a clean 404 with no visible exception, so it looks like a routing problem rather than a parameter-binding one. Always read these via `$request->route('paramName')` instead. (A route-bound parameter typed `int` also throws a `TypeError` under Laravel's reflection-based dispatch even with no `declare(strict_types=1)` anywhere in the app — use `string` and let Eloquent/SQLite handle the numeric string.) This has bitten the codebase twice now — check for it first whenever a school-subdomain route with its own path parameter 404s or looks up the wrong record.
- **Support access is audited impersonation, never a backdoor** (design decision 2026-07-09, the user explicitly asked "do we create a backdoor or not"). The platform admin signs in AS the target user with that user's own permissions (no elevation), every start/end is written to the audit trail, and a persistent banner shows for as long as it is active. Follow this pattern for any future "help a school with an issue" feature — don't reach for shared credentials or a hidden override.
- **SMTP is admin configurable, not just `.env`** (2026-07-09): `MailSettingsService` reads platform defaults from `platform_settings` and an optional per-school override from tenant `settings`, applied at runtime via `Config::set` (platform in `AppServiceProvider::boot()`, school override in `ResolveTenant` after the tenant connection is set). Every transactional email renders through the shared `resources/views/emails/layout.blade.php` (table-based, inline styles — most email clients strip `<style>` blocks) with a plain text alternative via `emails/plain.blade.php`. Any new Mailable should use this layout, not raw `nl2br()` strings.
- **A new tenant migration never reaches an already-provisioned school on its own** (found the hard way 2026-07-11: a live 500 on the user's real "greenfield" school, `houses.is_active` existed in the migration file but not in that school's actual database). `TenantManager::provision()` only runs tenant migrations at creation time; every school provisioned before a new file lands under `database/migrations/tenant/` needs it applied separately. **Run `php artisan tenants:migrate` (loops every provisioned school) immediately after adding or changing any tenant migration**, including against the local dev database, not just in the deploy runbook. Forgetting this is silent until a school actually hits the missing column/table, which then looks like an application bug rather than a missed migration step.
- **A new `extra_permissions` entry never reaches an already-cloned school role on its own, the same shape of bug as the tenant migration gotcha above** (found live 2026-07-11 while QA'ing the Report Card review workflow: added `report_cards.assign_review`/`report_cards.release`, but `school-owner` on a real school still got a 403). `RbacSeeder::syncTemplateRoles()` only updates the shared **template** roles (`school_id = null`); `Rbac::cloneTemplateRole()` copies a template's permission set into a school-scoped row **once, at clone time**, so any school that cloned a role before the new permission existed is frozen without it, even if the template's grant is `'*'` (conceptually "everything"). **After adding or changing any `extra_permissions` (or any permission-catalog change), run `php artisan db:seed --class="Database\Seeders\RbacSeeder"` AND additively resync already-cloned wildcard roles** (`$role->permissions()->syncWithoutDetaching($template->permissions()->pluck('id'))` for every school-scoped role whose slug's config grant is `['*']` — never a destructive full `sync()`, that would silently undo a school's own intentional permission removals). Forgetting this is silent until a real user on a real school hits a 403 on a feature that should already be theirs.
- **A stale `module_states` row silently overrides a school's current plan, a third variant of the same shape of bug as the two above** (found live 2026-07-17 on the real "greenfield" school: `/finance/payments` and `/finance/fee-items` both 403'd immediately after shipping the Foundation Finance slice, even though `greenfield`'s plan correctly listed `finance` in its `modules` array and `Rbac::moduleState()` had already been fixed to fall back to the plan when no explicit override exists). Root cause: `BillingController::assignPlan()` writes an **explicit** `module_states` row (`enabled`/`disabled`) for every optional module the moment any admin ever assigns/changes a school's plan, and that explicit row always wins over the plan-fallback, permanently, even after the module catalog changes later. `greenfield` had been assigned Foundation back on 2026-07-16, a day *before* `finance` was a real module with any code behind it, so it was correctly written `disabled` at that time — and stayed `disabled` forever after, silently outliving the day `finance` actually shipped. **Whenever a module goes from "no real screen" to "has one" (i.e. gets added to a `Plan.modules` array for the first time), re-run `assignPlan()`'s own sync logic — loop every optional module, `setModuleState()` to enabled/disabled based on the school's *current* plan — for every already-provisioned school**, not just for the one module that changed, since this also silently self-heals any other module's stale row along the way. Forgetting this is silent until a real user on a real school hits a 403 on a feature their plan should already include, identical in shape to the extra_permissions gotcha but one layer lower (module state, not permission grant).
