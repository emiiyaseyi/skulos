**6. A new, previously-undocumented Blade compiler gotcha found and fixed, not by inspection but by a real test failure**: `@php($var = expr)` (the parenthesized, single-expression inline form) silently miscompiles when the SAME FILE also contains a genuine, separate `@php ... @endphp` BLOCK further down — Blade's block-form compiler appears to pair the inline directive's bare `@php` with that LATER block's `@endphp`, leaving everything in between (including `@extends`, `@section`, every other directive) as literal uncompiled text, which then fails as a raw PHP parse error ("unexpected token @") the moment the real parser hits the first still-`@`-prefixed directive. Hit in `examinations/structure.blade.php` specifically because that file already had a genuine `@php ... @endphp` block at line 24 before a new `@php($termWord = ...)` was added as line 1 for the term-wording sweep above — confirmed by directly compiling the raw template via `app('blade.compiler')->compileString()` and `php -l`-ing the output (this project's own established debugging technique for exactly this class of bug), which showed `@extends(...)` sitting completely uncompiled, literal, in the generated PHP. **Fixed, and the safe pattern going forward**: use the explicit self-closing block form `@php $var = expr; @endphp` (opens and closes on the same line, so it can never reach out and incorrectly pair with an unrelated LATER `@endphp` elsewhere in the file) instead of the parenthesized inline form, in any file that might also contain (now or later) a genuine multi-line `@php...@endphp` block. Every other file touched in this sweep was individually compile-verified the same way (16 files, only this one broke) before trusting the test suite's own result.

### Live queue (2026-09-11, superseded by the entry above) — Multi-role accounts: My Timetable ignored the active role (`f72fb04`)

Live user report after the multi-role switcher shipped: "there's switching issue as teachers cant access timetables again... no difference between user profile and switched profile, all the menu should switch too once it switch... a parent who is a teacher cant see child timeables and his own class/subject timetable."

**Root cause, confirmed**: `TimetableController::resolveMineGrid()` decided teacher-view-vs-family-view by checking `Staff::where('user_id', ...)->first()` — raw record existence, zero regard for which role was actually active. Granting a teaching role auto-creates a linked Staff record (the confirmed multi-role design), so once that record existed the Staff branch won permanently, even while actively switched to Parent — a parent who also holds a teaching role could never see their children's schedule again, only ever their own (empty, if unassigned) teaching one. **Fixed**: the Staff lookup is now suppressed only when the active role (`User::roleIn()`) is explicitly family-scoped, so a genuinely family-scoped session always gets the family view regardless of any Staff record sitting on the account; every other role keeps the exact pre-multi-role behavior.

**A real testing-methodology trap found and worked around while chasing this, worth remembering for any future test of role-switching across separate requests**: a first attempt at the regression test reused the SAME `User` object across sequential `actingAs()` calls (switch via POST, then a separate GET) and the test failed even though the fix was correct — because `actingAs()` injects that exact object onto the Auth guard for every subsequent simulated request in the test, and `User::roleIn()`'s cache lives on the object instance. Reusing one object across calls keeps that cache alive for the whole test, masking any real fix — this NEVER happens in real production, where a genuine HTTP request always resolves `Auth::user()` fresh from the DB with an empty cache. Fixed the test by calling `User::find($id)` fresh before each `actingAs()` call rather than reusing the original variable. **Any future test that switches roles then checks a SEPARATE subsequent request must do this**, or it risks a false pass/false fail unrelated to the code under test.

**The nav/menu side of the report investigated, not independently reproduced**: traced `User::roleIn()`, `TeacherScope`, `FamilyScope`, `RoleDashboard::build()`'s dispatch, and the role-switcher partial (`role-switcher.blade.php`) — all correctly read the active/switched role already, confirmed via a real end-to-end HTTP test (switch, then a genuinely fresh subsequent request) using `SESSION_DRIVER=array`'s actual singleton-Store persistence (verified directly: session values written in one request ARE readable in a later, separate request within the same store, contrary to an initial false suspicion). The most likely explanation for "no difference between profiles" is that this exact Timetable bug was the visible symptom driving the perception — it's one of the very few screens where a switch should produce an obviously different, nameable result. If the report recurs after this fix reaches production, it needs a fresh screenshot/repro rather than assumed still-broken, since nothing else in the switch/nav chain showed a defect on inspection.

**QA**: new `TimetableTest` case (`test_a_parent_who_also_holds_a_teaching_role_sees_the_right_grid_for_whichever_role_is_active`) walks the full arc — parent sees child's schedule, grant a teaching role while still parent (family view must survive the new Staff record), switch to teacher (no leaked family data), switch back (family view returns). ### Live queue (2026-09-11, superseded by the entry above) — Multi-role accounts: one login can hold and switch between several roles (`779feb9`)

User directive: "we have some users that they are both teacher and parent, add a feature to the admin setting that allows one account to serve as both parent and teacher. Also, add a feature that allow the school admin to also be a class teacher or subject teacher, or other roles in the account. For all these, the user will have a switch account button at the top to switch from one user role to another." Two design questions asked via `AskUserQuestion`, both answered: grant screen is **a new dedicated "Multi-role accounts" screen** (not folded into Role Management), and granting a teaching role to someone with no Staff record **auto-creates a linked Staff record**.

**Built**: `user_additional_roles` (platform DB, mirrors `user_permissions`'s shape — a per-user/per-school grant layered on top of the role system, `school_id`/`user_id`/`role_id` unique triple). A user's real primary role stays exactly `school_user.role_id`, one row per (school, user), completely untouched — additional roles are purely additive, never a second membership row. `MultiRoleAccountService::grantRole()`/`revokeRole()`; granting a teaching-scoped role auto-creates a linked `Staff` record when the grantee has none yet (the confirmed design decision). New `Multi-role Accounts` screen under Settings > Users, gated on a new `staff.manage_multi_role` permission, deliberately separate from Role Management per the user's own answer. `RoleSwitchController` + a top-bar role-switcher partial (mobile-friendly, matches the existing outside-click-close nav pattern): switching writes `session('active_role_{school}')`, re-validated against `user_additional_roles` on every read — a tampered/stale/revoked value silently falls back to the primary role, never trusted blindly. `User::roleIn()` — the one choke point ~30 call sites already depend on for "this user's current effective role" (`Rbac::check`, `RoleDashboard`, nav, `TeacherScope`/`FamilyScope`, the post-login redirect, ...) — is now session-aware, so every one of them respects a switch automatically with zero other code changes.

**The literal root-cause bug this feature traces back to, also fixed**: `AccountProvisioningService`'s two direct `syncWithoutDetaching()` calls silently overwrote an existing member's primary role pivot — Laravel's `BelongsToMany::syncWithoutDetaching()` calls `updateExistingPivot()` for an already-member user, an unconditional overwrite. A teacher provisioned a second time under a different role (e.g. as a parent, matching email) used to silently lose their teacher role with no warning. Replaced both call sites with a new `syncRole()` that grants an additional role via the new table instead of clobbering the primary one when the user is already a member under a different role.

**A real bug found and fixed while testing the switch itself, not by the user**: `roleIn()`'s session read was gated on `session()->isStarted()`, but `Illuminate\Session\Store::save()` resets that flag to `false` at the end of every request — so a role switch written in one request could never be read back by `roleIn()` once that request had finished saving, only while the writing request was still mid-flight. Invisible in production (every real `roleIn()` call happens from inside some request, before that request's own save), but broke a test that switched roles via one HTTP call then checked the effect via a second, separate call in the same method. Fixed by dropping the unnecessary guard — other session reads in this codebase (e.g. `session('impersonator_id')` for impersonation) don't gate on `isStarted()` either.

**QA**: new `MultiRoleAccountTest` (8/8: grant, teaching-role auto-creates Staff, non-teaching role doesn't, switching actually changes what `Rbac::check()` allows, cannot switch into an unheld role, revoking the active additional role falls back to primary, a teacher without the permission cannot grant, and the root-cause regression test itself). Regression swept across `RoleDashboardTest`/`RoleManagementTest`/`SchoolAdminManagementTest`/`StaffAutoLoginTest`/`PlanFeatureNavTest`/`PlatformFlowTest` — 138/138 passing, 0 regressions.

### Live queue (2026-09-11, superseded by the entry above) — Real root cause found for "auto-login only worked for some": every welcome/reset email was sent unguarded, one SMTP failure silently killed the rest of a batch

Direct follow-up to the staff-auto-login work above, live on `ppms.skulosapp.com` right after deploying it: user reported some staff still stuck on "no login yet," the ones that DID get a login only showed a synthetic placeholder email (`staff-2@staff.ppms.skulos.local`) when the school's `staff_identifier` is "both," no way to see which identifiers actually work or whether the password had been changed, and "i dont want to click create for every teacher... should be auto created."

**Real root cause found, not guessed**: `AccountProvisioningService::provision()`/`provisionAuto()`/`resetPassword()` all sent their welcome/reset email **synchronously and completely unguarded** — `Mail::to(...)->send(...)` with no try/catch, and `AccountCreatedMail` is not `ShouldQueue`. A single transient SMTP failure (a real, plausible thing on shared hosting) throws straight out of `provisionAuto()`, which in `accounts:backfill-logins`' per-school loop (and in `StaffController::store()`) had no per-record guard either — so ONE failed send silently killed every remaining staff member in that school's backfill pass, exactly matching "it only worked for some." Fixed at the source: new `AccountProvisioningService::sendSafely()` wraps every mail send, logs a warning on failure, and never lets a notification failure block the account itself from being created — the account and its role are already saved by the time the email attempt runs. `accounts:backfill-logins` also now wraps each record in its own try/catch (defense in depth beyond the source fix), reporting exactly which records failed and why instead of the whole run silently stopping partway, and is safe to re-run to pick up only what's still missing.

**Never show the synthetic placeholder email, ever**: `users.email` is a platform `NOT NULL`+`unique` column, so a phone-only account still technically needs *something* stored there — but nothing user-facing should ever display it. The Staff profile's Login card now reads identifiers straight from `$staffMember->email`/`$staffMember->phone` (the real, admin-entered fields, never synthetic) instead of the login's own `User.email`, listing both together when both are on file — directly answering "what i expect to see here is what the staff can use to login (email address and phone number)."

### Live queue (2026-07-30, announcement/broadcast emails now queued, not sent inline — Codex audit item 2)

After the report card revert, user said "CONTINUE" — moved to the next item on the priority list I gave them (mobile table-stacking was item 1, now done): synchronous bulk email/broadcast sends, a real timeout risk for a large "all audience" send, not theoretical (a school-level announcement to "all" can plausibly reach 500-3,000+ recipients; the platform admin broadcast multiplies that across every matched school in one request).

Found two inline `Mail::send()` loops: `CommunicationService::emailAnnouncement()`/`sendEmail()` (school-level announcements/broadcasts, feeding `AnnouncementController::store()` and `MessageController::store()`), and `Admin\BroadcastController::send()` (the platform-wide leadership broadcast, the worse of the two since it loops every matched school). Neither `app/Jobs/` nor any `ShouldQueue` implementation existed anywhere in the codebase before this, net new pattern.

**Fixed**: two new jobs, `SendAnnouncementEmailJob` and `SendPlatformBroadcastEmailJob`, both `ShouldQueue`. `CommunicationService` now creates each `CommunicationLog` row (already had a `STATUS_QUEUED` status that was set but never actually meant, a synchronous send followed almost immediately) and dispatches a job per recipient instead of calling `Mail::send()` inline; `BroadcastController::send()` does the same. A queue worker has no "current tenant" at all when it picks up a job, unlike an HTTP request (`ResolveTenant` middleware never ran), so `SendAnnouncementEmailJob::handle()` explicitly resolves the `School` from the platform DB and calls `TenantManager::connectTo()` itself before touching the tenant-scoped `CommunicationLog`. **Return value semantics changed on purpose, not just internally**: `emailAnnouncement()`/`sendEmail()`/`dispatchAnnouncement()` used to return real `sent`/`failed` counts, honest under the old inline-send code, since the counts were known by the time the method returned. ### Live queue (2026-07-30, backup restore made safe — a real hazard from an external Codex code/UI audit)

**Fixed** (`7e039ab`): `BackupService::restoreMysql()` used to `DROP DATABASE` the live tenant database, THEN import the backup — if the import failed partway, the school was left with an empty database and no way back. The SQLite path had the same shape of bug: it overwrote the live `.sqlite` file directly with `file_put_contents()`, so a corrupt/truncated backup file could leave the live file broken. Both now write-verify-swap instead:
- **SQLite**: restore into a temp file (`{target}.restoring-{uniqid}`), run a real `PRAGMA integrity_check` against it, only `rename()` it over the live file (a single directory-entry swap, not a byte-by-byte overwrite) if that passes. Any failure cleans up the temp file and throws, live file untouched.
- **MySQL**: import into a throwaway `{db}_restoring_{timestamp}` database first. Only once `mysql` actually succeeds does `swapMysqlDatabase()` move it into place, via one atomic multi-table `RENAME TABLE` statement (MySQL has no `RENAME DATABASE`). The live database's own current tables are moved aside into a timestamped `{db}_before_restore_{Ymd_His}` database first — a real safety net, deliberately kept rather than dropped, at the cost of disk space until an admin or a future retention job clears it — not thrown away until the new data is already confirmed in place.

Both restore controllers (`School\BackupController`, `Admin\BackupAdminController`) now catch a failed restore and flash a clear `session('error')` message instead of a raw 500, since a failed restore is now a normal, recoverable outcome, not something that should never happen.

- **Every list/index screen gets bulk actions, not just single-row ones** (user directive 2026-07-11, given after the houses reactivate bug report: "add a bulk option to do the reactivate, delete, retire at once with a check box... this is the way I want every of my builds to look like"). Any screen that lists rows a user can act on one at a time (retire, reactivate, delete, assign, etc.) should also let them tick several and act on all of them in one request, not just one row at a time. Reference implementation: `school.houses.index` (`backend/resources/views/school/houses/index.blade.php` + `HouseController::bulkAction()`), built 2026-07-11. Pattern: a per-row checkbox named `thing_ids[]`, a header "select all" checkbox, and an action bar of submit buttons, all wired via the HTML5 `form="idOfBulkForm"` attribute pointing at an out-of-band `<form id="idOfBulkForm">` placed outside the `<table>`, not wrapping the table in its own `<form>`. This matters because existing per-row single-action forms (a "View" link, a "Retire" button, a "Remove" button) already live inside each row's `<td>`, and HTML forms cannot nest, so the bulk checkboxes must associate with their form by `id`/`form` attribute rather than physical nesting. A small vanilla script (no framework) handles "select all" and a "tick at least one first" guard before submit; the server route validates `min:1` regardless. Apply this pattern going forward to Students, Staff, and any other list screen as they get bulk-eligible actions, rather than building single-row-only controls and needing to retrofit bulk support later.
- **No dashes in on-screen text** (user directive 2026-07-08, restated firmly). User-facing copy must not use hyphens or em/en dashes as punctuation — the user considers it an "AI-generated" tell. This includes text rendered via **CSS `content:` values** and **`aria-label`/`title`/`alt` attributes**, not just `>text<` nodes. When sweeping, check all three: text nodes, CSS `content`, and rendered attributes. Code comments do not render and are exempt. Verify with byte-level checks using unicode escapes (`—` em, `–` en), not literal characters piped through a shell — the shell can mangle the char so a naive check reports a false "0 remaining" (this bit us once on 2026-07-08). **Exemption confirmed 2026-07-10:** a hyphen inside a standard, correctly-spelled compound term (e.g. "Pre-Nursery") is fine — the rule targets dashes used as clause-separating punctuation (the "AI tell"), not hyphens that are genuinely part of how a word is normally spelled. When in doubt whether a term is "standard," ask rather than silently rewriting it (e.g. to "Pre Nursery") or silently leaving it as is.
- **No section sign character anywhere** (user directive 2026-07-10). Spell it out: write "section 14" rather than the symbol form. Applies everywhere, including planning docs like the tracker and this file, not just product UI copy.
- **Thorough QA after every item build** (user directive 2026-07-08). After finishing each build item, before declaring it done, run a real QA pass and record it in the tracker: (1) run tests / exercise the actual behavior, note issues, bugs, DB errors; (2) ask and answer honestly: *Did I fully solve what the user asked? Did I miss anything they requested? Did I change or break something I should not have touched? Is anything half-done or faked?* Fix what QA surfaces before moving on. This is not optional polish; it is part of "done."
- **Nothing hardcoded — ever** (user directive 2026-07-08, reinforcing docx TD-007 / "Configuration Before Customization"). Anything a school or the Platform Super Admin could plausibly want to change — pricing, plan features, grading formulas, role permissions, module lists, contact details, copy, term counts, thresholds — must live in config, the database, or admin-editable settings, never as literals baked into code paths. The `config/skulos.php` catalog + per-school `settings` table + module/permission tables are the sanctioned homes for this. If you find yourself typing a business value into a controller or view, stop and move it.
  - **Restated more precisely 2026-07-12, after the score-range comment bank was first built reading straight from `config('skulos.default_comment_bank')` with no way for a school to edit it:** "everything must be a DB-backed layer, which means an admin/school/user should be able to customize their own." A `config/skulos.php` array is only ever acceptable as the **seed/default catalog**, never as the live, read-at-runtime source of truth for anything a school might reasonably want to add to, edit, or turn off. The correct shape, already established by `grading_scales`/`grading_bands` (seeded once from `config('skulos.default_grading_scales')`, then a real tenant table an admin edits from there) and now `comments` (seeded from `config('skulos.default_comment_bank')` into a real tenant table): config feeds an explicit one-time (or idempotent) seed action into a tenant database table, and every runtime read goes through that table, never through `config()` directly, once seeded. When adding a new "default catalog of things a school might want to tweak," build it this way from the start rather than reading config live and needing a follow-up fix.
- **Security in everything:** deny-by-default access checks, explicit `$fillable` (no `$guarded = []`), sensitive/hidden attributes excluded from audit logs and serialization, tenant isolation preserved even for logs, no raw SQL with interpolated input (the one `CREATE DATABASE` statement uses a slug sanitized to `[a-z0-9_]`), 404 (not 403) for resources whose existence shouldn't leak.
- **Always commit AND push at every completed item** (user directive, restated 2026-07-08, restated again 2026-07-16: "ALWAYS COMMIT AFTER EVERY TASK IS DONE"). - **Domain routing + route parameters gotcha (found 2026-07-09, recurred and re-fixed the same day in `BackupController`).** On any route under `Route::domain('{school}.'.$domain)` that also has its own path parameters (e.g. `/campuses/{campusId}`), do **not** declare those as typed method parameters on the controller action (`function destroy(Request $request, string $campusId)`). Laravel resolves untyped/scalar controller parameters **positionally** against the full route parameter list, domain parameter included, not by name — so `$campusId` silently receives the school's slug instead. It fails quietly: `findOrFail()` on the wrong value throws `ModelNotFoundException`, which Laravel renders as a clean 404 with no visible exception, so it looks like a routing problem rather than a parameter-binding one. Always read these via `$request->route('paramName')` instead. (A route-bound parameter typed `int` also throws a `TypeError` under Laravel's reflection-based dispatch even with no `declare(strict_types=1)` anywhere in the app — use `string` and let Eloquent/SQLite handle the numeric string.) This has bitten the codebase twice now — check for it first whenever a school-subdomain route with its own path parameter 404s or looks up the wrong record.
- **Support access is audited impersonation, never a backdoor** (design decision 2026-07-09, the user explicitly asked "do we create a backdoor or not"). The platform admin signs in AS the target user with that user's own permissions (no elevation), every start/end is written to the audit trail, and a persistent banner shows for as long as it is active. Follow this pattern for any future "help a school with an issue" feature — don't reach for shared credentials or a hidden override.
- **SMTP is admin configurable, not just `.env`** (2026-07-09): `MailSettingsService` reads platform defaults from `platform_settings` and an optional per-school override from tenant `settings`, applied at runtime via `Config::set` (platform in `AppServiceProvider::boot()`, school override in `ResolveTenant` after the tenant connection is set). Every transactional email renders through the shared `resources/views/emails/layout.blade.php` (table-based, inline styles — most email clients strip `<style>` blocks) with a plain text alternative via `emails/plain.blade.php`. Any new Mailable should use this layout, not raw `nl2br()` strings.
- **A new tenant migration never reaches an already-provisioned school on its own** (found the hard way 2026-07-11: a live 500 on the user's real "greenfield" school, `houses.is_active` existed in the migration file but not in that school's actual database). `TenantManager::provision()` only runs tenant migrations at creation time; every school provisioned before a new file lands under `database/migrations/tenant/` needs it applied separately. **Run `php artisan tenants:migrate` (loops every provisioned school) immediately after adding or changing any tenant migration**, including against the local dev database, not just in the deploy runbook. Forgetting this is silent until a school actually hits the missing column/table, which then looks like an application bug rather than a missed migration step.
- **A new `extra_permissions` entry never reaches an already-cloned school role on its own, the same shape of bug as the tenant migration gotcha above** (found live 2026-07-11 while QA'ing the Report Card review workflow: added `report_cards.assign_review`/`report_cards.release`, but `school-owner` on a real school still got a 403). `RbacSeeder::syncTemplateRoles()` only updates the shared **template** roles (`school_id = null`); `Rbac::cloneTemplateRole()` copies a template's permission set into a school-scoped row **once, at clone time**, so any school that cloned a role before the new permission existed is frozen without it, even if the template's grant is `'*'` (conceptually "everything"). **After adding or changing any `extra_permissions` (or any permission-catalog change), run `php artisan db:seed --class="Database\Seeders\RbacSeeder"` AND additively resync already-cloned wildcard roles** (`$role->permissions()->syncWithoutDetaching($template->permissions()->pluck('id'))` for every school-scoped role whose slug's config grant is `['*']` — never a destructive full `sync()`, that would silently undo a school's own intentional permission removals). Forgetting this is silent until a real user on a real school hits a 403 on a feature that should already be theirs.
- **A stale `module_states` row silently overrides a school's current plan, a third variant of the same shape of bug as the two above** (found live 2026-07-17 on the real "greenfield" school: `/finance/payments` and `/finance/fee-items` both 403'd immediately after shipping the Foundation Finance slice, even though `greenfield`'s plan correctly listed `finance` in its `modules` array and `Rbac::moduleState()` had already been fixed to fall back to the plan when no explicit override exists). Root cause: `BillingController::assignPlan()` writes an **explicit** `module_states` row (`enabled`/`disabled`) for every optional module the moment any admin ever assigns/changes a school's plan, and that explicit row always wins over the plan-fallback, permanently, even after the module catalog changes later. `greenfield` had been assigned Foundation back on 2026-07-16, a day *before* `finance` was a real module with any code behind it, so it was correctly written `disabled` at that time — and stayed `disabled` forever after, silently outliving the day `finance` actually shipped. **Whenever a module goes from "no real screen" to "has one" (i.e. gets added to a `Plan.modules` array for the first time), re-run `assignPlan()`'s own sync logic — loop every optional module, `setModuleState()` to enabled/disabled based on the school's *current* plan — for every already-provisioned school**, not just for the one module that changed, since this also silently self-heals any other module's stale row along the way. Forgetting this is silent until a real user on a real school hits a 403 on a feature their plan should already include, identical in shape to the extra_permissions gotcha but one layer lower (module state, not permission grant).
