## Design System Rules (standing instructions — apply to every future build, marketing site and product UI alike)

Established 2026-07-26 from direct feedback on the first landing page draft. These are not one-off fixes — apply them by default to every card, section header, and tagline built from here on, across the marketing site and the eventual product UI, unless a future instruction explicitly overrides them.

- [ ] **Cards (feature/capability/module/pricing cards, etc.):** icon and title are always **center-aligned**; the supporting body text underneath is always **justified** (`text-align: justify`), never left-aligned.
- [ ] **Section headers and taglines** (eyebrow label + heading + intro paragraph): same rule — the eyebrow/heading is **center-aligned**, the accompanying paragraph/tagline text is **justified**.
- [ ] **Grid layouts** should always resolve to complete rows/columns — pick item counts and column counts that divide evenly at each breakpoint (e.g. 9 items → 3×3, 12 items → 4×3 desktop / 2×6 tablet), rather than leaving a dangling partial last row. Add or trim content to make the grid land clean, don't just let `auto-fit` produce an orphan.
- [ ] Keep section vertical spacing tight and deliberate — avoid excess empty space between sections; this was flagged directly as a problem on the first draft.
- [ ] **Nothing hardcoded — ever** (user directive 2026-07-08). Any value a school or the Platform Super Admin could plausibly want to change (pricing, plan features, grading formulas, permissions, module lists, contact info, copy, term counts, thresholds) lives in config/database/admin settings, never as literals in code. This applies to every layer: backend, frontend, marketing site.
- [ ] **No dashes in on-screen text** (user directive 2026-07-08). Hyphens and em/en dashes must not appear as punctuation in any user-facing copy (marketing pages, UI labels, validation and error messages, notifications, report card text). Rephrase with commas, colons, or separate sentences. Existing marketing-site copy predates this rule and needs a sweep when next touched.

## Architecture decision (2026-07-09): app UI is Laravel-rendered for now

To make the platform clickable from **one entry point** fast, the product UI is built as **Laravel server-rendered Blade pages** (reusing the design system), not the separately-planned Next.js SPA + REST API. Rationale: one deployable, cPanel-friendly, reuses the tenancy/RBAC/audit/services already built, and reaches a working unified platform far quicker than standing up a separate SPA + token auth + CORS + two deployments. **API-first is preserved** — the services (TenantManager, Rbac, ResultService, NotificationService, importers, etc.) are UI-agnostic, so a Next.js frontend consuming a REST/JSON API can be layered on later without rework. If/when that happens, the Blade UI can remain for admin or be retired. Recorded here so a future agent doesn't think the Next.js frontend was skipped by mistake.
